MFU AI Teaching Assistant

General Styles and Coding Standards

This document defines the coding standards for the MFU AI Teaching Assistant project, with the aim of ensuring consistency and quality across the main application layers. By following a unified coding style, the project promotes clear and readable code, making it easier for developers to understand, review, and maintain the system. These standards help reduce regressions during feature development and ongoing maintenance by encouraging structured and predictable implementation practices.

1. Purpose

The project includes role-based user access, study support features, AI-assisted workflows, reminders, document handling, and administrative controls. Because the system contains both user-facing and service-side logic, consistency is required in naming, request handling, validation, permission checks, error handling, data updates, and security behavior.

In practical use, the system supports student learning tasks such as question answering, study planning, flashcard and quiz generation, reminder scheduling, and access to course materials. It also supports teacher and administrative workflows such as course management, content organization, analytics, audit logging, and protected data operations. Since these features depend on shared helpers, route handlers, database queries, and AI request flows, inconsistent code style can quickly make maintenance harder and increase the risk of logic errors.

These standards are intended to keep future work aligned with the existing implementation style and to make onboarding easier for new contributors. The focus of this document is practical consistency rather than theory.

2. Naming Standards (Project-Enforced)

2.1 Naming Variables

Variable names should be clear, complete, and meaningful. Application variables use camelCase. Names should describe the role of the value rather than only its type.

Variable Name Meaning Style
selectedModel Currently selected assistant model noun with modifier
currentConversationId Current conversation identity noun with modifier
reminderText Reminder message content noun with modifier
requestedCourseId Course identity requested by client noun with modifier

2.2 Naming Convention for Functions

Function names should begin with a verb and describe the action they perform. Helper functions should remain short and direct. Retrieval helpers typically use prefixes such as get, read, load, or create.

Function Name Verb Object
createClient create client
requireAdminUser require admin user
trackApiError track API error
queueReminderNotificationJobs queue reminder notification jobs

2.3 Naming Constants

Constants with system-wide meaning should use uppercase letters with underscores.

Constant Name Purpose
UUID_REGEX Validates UUID-like values
AUTH_PATHS Defines authentication routes
PUBLIC_PATHS Defines public routes
NEXT_PUBLIC_SUPABASE_URL Defines the backend connection setting

2.4 Naming Boolean Variables

Boolean values should read like conditions. Preferred prefixes are is, has, and can.

Variable Name Meaning
hasUserDocumentAccess Checks whether persistence is allowed for the user
canPersist Checks whether the conversation should be stored
isAuthenticated Checks whether a valid session exists

2.5 Naming Types and Components

Shared types and components use PascalCase. This keeps interfaces, unions, and component symbols visually distinct from local variables.

Name Category
Profile Type
CourseMaterial Type
ModelConfig Type
ChatInterface Component

3. API Layer Standards

3.1 Route Handler Design

  • Keep route handlers focused on request parsing, validation, permission checks, orchestration, and response output.
  • Move reusable logic into shared helpers when the same behavior can appear in multiple endpoints.
  • Return JSON responses with clear success or error shapes.
export async function GET() {
  const supabase = await createClient()
  const { data: { user } } = await supabase.auth.getUser()

  if (!user) {
    return NextResponse.json({ error: "Unauthorized" }, { status: 401 })
  }

  return NextResponse.json({ ok: true })
}

3.2 Auth and Permissions

  • Protected endpoints must verify the current user before reading or mutating data.
  • Role checks must be applied for student-only, teacher-only, and admin-only actions.
  • Ownership or enrollment must be validated before accessing user-scoped or course-scoped records.
if (!profile || profile.role !== "student") {
  return NextResponse.json({ error: "Only students can create reminders" }, { status: 403 })
}

3.3 Path and Query Parameters

  • Path parameters should identify the main resource.
  • Query parameters should be used for filters, selection, or simple options.
  • Request body values should be normalized with trimming and explicit conversion where needed.

4. Data Access Standards

4.1 Scope

  • Data queries should remain explicit and readable.
  • Use single-row selection helpers only when exactly one row is expected.
  • Order result sets when the output is shown to users.

4.2 Write Pattern

Writes should validate input first, then perform the insert or update, then return the saved data needed by the client. 

const { data: reminder, error } = await supabase
  .from("study_reminders")
  .insert({
    student_id: user.id,
    course_id: courseId,
    reminder_text: reminderText,
    reminder_time: reminderTime,
  })
  .select()
  .single()

4.3 Partial Updates

Partial updates should only include fields that were actually provided. Empty strings should be normalized where needed, and update payloads should remain small and explicit.

5. Model and Schema Standards

5.1 Shared Types

  • Use shared typed structures for profiles, courses, reminders, documents, and configuration.
  • Role values should be restricted to the allowed set of system roles.
  • Nullable values should be marked clearly.

5.2 Persisted Field Naming

Persisted fields use snake_case. This applies to stored database fields and stored metadata values.

Field Name Meaning
created_at Creation timestamp
course_id Course identity link
reminder_time Scheduled reminder time
resource_type Audit log resource category

6. Error Handling Standards

6.1 HTTP Errors

  • Use 400 for invalid input.
  • Use 401 when the user is not authenticated.
  • Use 403 when the user is authenticated but not allowed to perform the action.
  • Use 500 for unexpected internal failures.

6.2 External Operations

External operations such as notification scheduling, document indexing, or AI generation should be wrapped so the system can return a controlled error instead of failing silently. 

try {
  const queuedJobs = await queueReminderNotificationJobs(...)
  return NextResponse.json({ reminder, queuedJobs: queuedJobs.length })
} catch (error) {
  return NextResponse.json({ error: "Failed to queue reminder notification" }, { status: 500 })
}

7. Shared Helper Standards

7.1 Session and Database Helpers

  • Use a shared client creation helper for authenticated server access.
  • Use a shared admin guard helper for admin-only operations.
  • Keep route files from re-implementing the same session logic repeatedly.

7.2 Logging Helpers

  • Use a shared error tracker for unexpected API failures.
  • Use a shared audit logger for important write actions.
  • Logging should be structured and purposeful.

8. Security Standards

8.1 Authentication

  • Authentication must be checked server-side before returning private data.
  • Role-based redirects should be controlled centrally.
  • Admin access must use a stricter verification step.

8.2 Secrets and Configuration

Sensitive values must come from environment configuration and must not be hardcoded in application logic.

Configuration Name Purpose
NEXT_PUBLIC_SUPABASE_URL Application backend connection
NEXT_PUBLIC_SUPABASE_ANON_KEY Authenticated client access
DO_SPACES_BUCKET Document storage bucket
DO_SPACES_SECRET Private storage credential

8.3 Protected Data Access

  • Private document access should use controlled read URLs.
  • Audit records should be written for significant actions.
  • Permission checks should be applied before exposing course or user data.

9. Database Migration Standards

  • Schema changes must be applied through migration files.
  • New tables should define keys, constraints, and clear relationships.
  • Security rules should be added together with schema changes.
  • Indexes should be added for common lookup or ordering patterns.
create table if not exists public.notification_jobs (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null,
  channel text not null,
  template text not null,
  payload jsonb not null default '{}'::jsonb,
  status text not null default 'queued'
);

10. Testing Standards

10.1 Scope

  • Core flows should be covered by type checks, build checks, and smoke checks.
  • Critical route and schema behavior should be verified before release.
  • Regression checks should focus on access control, reminders, chat, and document features.

10.2 Current Validation Commands

Command Purpose
npm run type-check Type safety validation
npm run lint Static code quality validation
npm run build Production build validation
npm run test:roadmap Critical smoke checks

11. Service and AI Standards

11.1 Service Responsibilities

  • Service helpers should keep one clear responsibility.
  • Model configuration should remain centralized.
  • Document, reminder, and logging services should stay separate from UI state logic.

11.2 AI Request Rules

  • AI prompts should be shaped by the user role and the request purpose.
  • Context should be prepared before the model call.
  • Generated output should be validated before it is stored or returned as structured data.
const result = await ai.models.generateContent({
  model: "...",
  contents: "Generate a study plan as a JSON array"
})

12. Timestamp and Data Consistency Standards

12.1 Timestamp Storage

  • Creation and update times should be stored consistently across records.
  • Time values should follow one clear storage format so that frontend and backend behavior remain aligned.
  • Inserted records should preserve reliable creation timestamps for later review and reporting.

12.2 Ordered Output and Query Consistency

  • Ordered output should use explicit time-based sorting when users expect chronological results.
  • Lists such as reminders, documents, messages, and logs should not rely on implicit database ordering.
  • When multiple records are shown together, the selected ordering rule should remain stable and predictable.

12.3 Schedule and Reminder Normalization

  • Stored schedule times should be normalized before persistence.
  • User-provided date and time values should be validated before they are inserted into reminder or planning data.
  • Invalid or past schedule values should be rejected before they affect notification workflows.

12.4 Audit and Traceability Rules

  • Audit and reminder records should preserve enough data for tracing system behavior later.
  • Important actions should keep actor, action type, related resource, and time reference in a consistent form.
  • Data written for observability should be useful for debugging, review, and accountability without becoming ambiguous.
